# Beyond the Org Chart: Theoretical Foundations for a Simpler Multi-Agent Coding Framework

## TL;DR
- **The thesis is right but incomplete.** Importing human org-chart topology (Mayor → Witness → Deacon → Dogs) onto aligned, high-bandwidth LLM agents is largely a category error — but Gastown's load-bearing parts are *already* disguised distributed-systems primitives (failure detectors, a serializing merge queue, a supervision tree, a market). The win is not to invent something exotic from chaos theory; it is to **replace the anthropomorphic scaffolding with the boring, named primitives it is imitating**, and delete the rest.
- **Most multi-agent failures are coordination/design failures, not model failures.** Cemri et al., "Why Do Multi-Agent LLM Systems Fail?" (arXiv:2503.13657, UC Berkeley Sky Computing Lab, NeurIPS 2025), analyzing 1,642 annotated execution traces, found "41% to 86.7% failure rate on 7 state-of-the-art (SOTA) open-source MAS," with failures distributed as System Design 44.2%, Inter-Agent Misalignment 32.3%, and Task Verification 23.5% — so the highest-leverage primitives are *verification/quality gates, state persistence, and conflict-free parallel work*, not richer hierarchy.
- **Recommended blueprint:** a **shared-state blackboard (git/ledger) + content-addressed work tickets + optimistic parallel work in worktrees + a single serializing merge queue with hard CI gates + best-of-N-with-a-real-verifier + flat orchestrator-worker spawning + crash-only/idempotent restart**. This keeps ~5 sound mechanisms and discards the municipal cast. Redundancy ("more agents") is principled *only when paired with a selection/fitness mechanism* (tests, a verifier); otherwise it amplifies error.

## Key Findings

1. **Gastown is a hybrid in disguise.** Its watchdog chain (Boot→Deacon→Witness, heartbeats every 3 min) is a *failure detector*; its Refinery (Bors-style bisecting merge queue) is *linearizability/serialization of writes to main*; its Escalation tree is an *Erlang/OTP supervision tree*; its Wasteland (reputation-stamped federation) is *market/mechanism design*; its Beads ledger (now on Dolt, git-versioned) is *event sourcing / a durable log*. The Mad-Max naming obscures that the engineering core is sound distributed systems. The org-chart layer on top — personas, role hierarchy, severity-routed chains of command — is the part motivated by human-org analogy, and it is the most questionable.

2. **Human hierarchy exists to fix human limits that aligned agents largely lack.** Org charts, military command, and span-of-control rules evolved to compensate for low human communication bandwidth, ego/conflict, partial goal alignment, and limited attention. Aligned LLM agents can be spawned goal-aligned, communicate through a shared store at high bandwidth, and carry no ego. So the *reasons* for hierarchy are weaker — but two human-org functions survive translation because they map onto real machine problems: **failure/drift detection** (an agent that hallucinates or stalls is like a node that has crashed or partitioned) and **write serialization** (parallel writers to one repo is a concurrency-control problem).

3. **The dominant failure modes are organizational, and they tell you exactly which primitives to keep.** The MAST taxonomy's three failure classes — System Design (44.2%), Inter-Agent Misalignment (32.3%), Task Verification (23.5%) — map directly to: (a) durable shared state + clear task specs, (b) shared-state/blackboard coordination to avoid miscommunication, and (c) verification gates. Notably the single largest individual failure mode was *Step Repetition (15.7%)*, an idempotency/state problem, and verification failures (No/Incomplete Verification 8.2% + Incorrect Verification 9.1%) together (~17%) are a quality-gate problem. None of these are fixed by adding a Deacon.

4. **The distributed-systems canon supplies a clean, minimal primitive for each genuine need** (full mapping in Details). The most important: a **failure detector** (phi-accrual/heartbeat) to detect drift; a **serializing merge queue** (linearizability) to make `main` correct; **CRDTs / git three-way merge** for conflict-free parallel edits; **event sourcing / a durable log** for crash recovery; **idempotency keys** to stop duplicate/repeated work; **quorum/voting (Byzantine-inspired)** to catch hallucination; **crash-only / "let it crash"** restart instead of elaborate escalation.

5. **Game-theory mechanisms are mostly the wrong tool for *aligned* agents.** Auctions, the Contract Net Protocol, Shapley-value credit assignment, incentive-compatibility, and principal-agent contracts all assume *self-interested* agents that may misreport. Aligned cooperative coding agents are a *pure coordination* problem, not a *competition* problem, so most of mechanism design is unnecessary overhead. The exceptions worth borrowing are the *non-strategic* parts: the Contract Net's *capability-based task routing* (announce → bid by fitness → award) as a load balancer, and Schelling/focal points (shared conventions like file layout) to coordinate without communication.

6. **Swarm/stigmergy is appealing but only pays off under locality.** Ant-colony stigmergy (coordination via traces in a shared environment) maps elegantly onto agents reading/writing a shared ledger — this is the blackboard pattern. But stigmergic/emergent coordination only beats explicit coordination when *tasks are reasonably independent*; if every edit to module A invalidates B–Z, the system thrashes. For coding, this argues for **decomposing work to maximize locality** (independent files/modules) and using shared state, not for a literal pheromone simulation.

7. **Complexity/chaos theory is a *diagnostic lens*, not an implementation.** "Edge of chaos" / self-organized criticality explains *why* you want a regime between rigid hierarchy (too ordered, brittle, slow) and unmanaged agent swarms (too chaotic, the $100/hr "murderous rampaging Deacon" failure mode). The practical translation is **control theory**: closed feedback loops (CI as the sensor, merge gate as the actuator), backpressure/concurrency limits (a governor), and observability — not literal criticality tuning.

8. **Redundancy is principled — but only with a selection mechanism.** Best-of-N, ensembles, and speculative execution are sound *when an automatic verifier exists to pick the winner* (unit tests, compilers, a reward model). For coding this is unusually favorable because correctness is checkable. But naive consensus/majority voting falls into a "popularity trap" amplifying common-but-wrong answers; per Vallecillos-Ruiz, Hort & Moonen, "Wisdom and Delusion of LLM Ensembles for Code Generation and Repair" (arXiv:2510.21513), "a diversity-based strategy realizes up to 95% of this theoretical potential," while consensus selection "falls into a 'popularity trap,' amplifying common but incorrect outputs," and the ensemble upper bound "can be 83% above the best single model." The real design axis is **exploration (redundancy) vs. exploitation (coordination)**, gated by whether you have a fitness function.

## Details

### A. Why the human-org framing is a category error (and where it isn't)

Human coordination structures are *compensating mechanisms*. A corporate hierarchy limits each manager's span of control because humans cannot track dozens of direct reports; chains of command exist because broadcast communication is expensive and humans distort messages; politics and incentive schemes exist because humans are self-interested and partially aligned. LLM coding agents invert most of these constraints: they can be instantiated from the same prompt/goal (high alignment), they can all read the same shared state cheaply (high bandwidth, no telephone-game distortion), and they have no career incentives to misreport. Yegge's own framing — Mayor as project manager, Polecats as gig workers, a Deacon patrolling for misbehavior — is explicitly anthropomorphic, and that is the layer the user is right to suspect.

However, two functions that hierarchy *implements* in human orgs correspond to genuine machine problems and must be preserved in *some* form:
- **Detecting a member who has stopped contributing or gone rogue.** In humans this is management; in distributed systems it is a **failure detector**. An LLM agent that fills its context window and stalls, loops, or drifts into hallucination is functionally a crashed or Byzantine node.
- **Preventing simultaneous conflicting changes.** In humans this is process/sign-off; in distributed systems it is **concurrency control / linearizability**. Gastown's Refinery is exactly this.

So the correct reframing is: *keep the two real distributed-systems functions, implement them with named primitives, and delete the org-chart metaphor that bundles them with unnecessary personas and command tiers.*

### B. Distributed-systems primitives → agent-coordination functions (the core mapping)

- **Failure detectors (heartbeats, phi-accrual).** Mechanism: nodes are suspected dead when heartbeats lapse; phi-accrual outputs a *suspicion level* rather than a binary, tunable against network jitter. Agent mapping: detect a stalled/looping/drifting agent. *Why it works:* drift is observable as the absence of progress signals (no new commits, no ledger writes, repeated tokens). This replaces the Witness/Deacon with a few lines of timeout logic. **Keep — this is load-bearing.**
- **Leader election (Raft/Paxos/viewstamped replication).** Mechanism: when the leader's heartbeat lapses, followers time out and elect a new leader by majority vote; Raft decomposes into leader election + log replication + safety and tolerates ⌊(N−1)/2⌋ failures. Agent mapping: if the *orchestrator* dies, promote a worker; or "re-elect" the agent responsible for a task when the incumbent drifts. *Why it works:* makes coordinator failure a non-event. For a single-user coding tool this is usually overkill — a supervisor restart is simpler. **Borrow only at multi-node scale.**
- **Linearizability vs. eventual consistency.** Mechanism: linearizable systems serialize operations through a single point so everyone sees one order; eventual-consistency systems let replicas diverge and reconcile. Agent mapping: `main` must be linearizable (one correct history) → a **single serializing merge queue**; agents' scratch work can be eventually consistent (worktrees). *Why it works:* you pay coordination cost only where correctness demands it. **Keep the merge queue; this is Gastown's best idea.**
- **CRDTs (conflict-free replicated data types).** Mechanism: data types whose concurrent updates are commutative/associative/idempotent, so replicas converge with no central arbiter (e.g., OR-Sets, LWW-registers, the Kleppmann JSON CRDT). Agent mapping: merge parallel agents' edits to *structured* shared state (task lists, status, knowledge) without conflict. *Why it works:* removes a whole class of merge coordination for metadata. Note: source code is *not* naturally a CRDT (semantic conflicts persist), so for code you still need tests + a merge queue; use CRDTs for the *coordination metadata*, not the program. **Keep for the ledger/state, not for code.**
- **Event sourcing / durable log (and CQRS).** Mechanism: persist the sequence of events as the source of truth; rebuild state by replay. Agent mapping: Beads/Dolt and `.events.jsonl` are exactly this — work survives agent death and can be audited/replayed. *Why it works:* gives crash recovery and observability for free. **Keep — this is the second-best idea in Gastown.**
- **Idempotency.** Mechanism: an operation applied twice has the same effect as once (idempotency keys dedupe retries). Agent mapping: directly attacks MAST's #1 failure mode, *Step Repetition (15.7%)*. Tag each work unit with a content/intent key; re-running a completed step is a no-op. *Why it works:* restarts and retries become safe. **Keep — cheap, high-value.**
- **Quorum / voting and Byzantine fault tolerance (PBFT).** Mechanism: BFT protocols reach agreement despite nodes that lie arbitrarily, typically needing 3f+1 nodes to tolerate f Byzantine ones. Agent mapping: a *hallucinating* agent is Byzantine — it asserts false things confidently. Cross-checking an answer across independent agents (voting/debate) catches some hallucinations. *Why it works:* independent errors are unlikely to coincide — *if* they're independent. Caveat: same-model agents make correlated errors, so voting is weaker than BFT's independence assumption; prefer an *objective* verifier (tests) over agent votes when available. **Borrow selectively for un-checkable outputs.**
- **The actor model + supervision trees ("let it crash").** Mechanism: isolated actors communicate by messages; a supervisor restarts/resumes/stops/escalates failed children; push risky work to leaves (the Erlang/OTP model that gave Ericsson famous availability). Agent mapping: each agent is an actor with isolated context (its own worktree/window); a thin supervisor restarts a stalled agent from durable state. *Why it works:* fault isolation + automated recovery without bespoke error handling. Gastown's Escalation is a supervision tree — but it has *too many tiers*. A single supervisor + restart-from-log captures ~all the value. **Keep one level; delete the multi-tier chain.**
- **SAGA pattern / compensating transactions.** Mechanism: a long transaction is a sequence of local steps, each with a compensating undo; on failure, run compensations backward. Agent mapping: a multi-step coding task (migrate DB → update API → update callers) where a late failure needs partial rollback. *Why it works:* gives atomicity-like behavior without global locks. For most coding work git revert *is* the compensation; reach for explicit sagas only for multi-system side effects. **Borrow rarely.**
- **Gossip/epidemic protocols, vector/Lamport clocks.** Mechanism: gossip spreads state in O(log N) rounds; logical clocks establish causal ("happens-before") ordering without synced wall clocks. Agent mapping: relevant only at federation scale (Wasteland-style many-instance coordination). For a single team's agents on a shared store, a central log makes these unnecessary. **Skip unless federating.**
- **Work-stealing schedulers.** Mechanism: idle workers steal tasks from busy workers' queues, balancing load with no central dispatcher. Agent mapping: idle agents pull the next ready ticket from a shared queue rather than a Mayor pushing assignments. *Why it works:* removes the central assigner (the "Mayor") and self-balances. **Keep — it deletes a role.**

### C. Game theory & mechanism design — mostly skip, borrow the coordination bits

The crucial distinction is **competition vs. coordination**. Mechanism design (auctions, the revelation principle, incentive compatibility, Shapley-value payments, principal-agent contracts) exists to make *self-interested* agents reveal truth and behave well despite divergent goals. The Shapley-Coop and SHAQ/SHARP lines of work apply this to *self-interested* LLM agents — explicitly the case where agents have "divergent but complementary goals." **For aligned cooperative coding agents this machinery is unnecessary** and adds complexity for a problem you don't have. You control the agents; you don't need to incentivize honesty, you can just instrument it.

What *is* worth borrowing is non-strategic:
- **Contract Net Protocol (Smith, 1980)** as a *task router*: announce a task, let agents "bid" with a cheap capability/confidence/cost estimate, award to the best fit. Stripped of strategic bidding, this is just capability-aware load balancing and pairs naturally with work-stealing.
- **Schelling/focal points**: shared conventions (canonical file layout, naming, "the test file lives next to the source") let agents coordinate *without communicating*, reducing the inter-agent-misalignment failures (32.3% in MAST). This is the cheapest coordination mechanism that exists — convention over communication.
- **Shapley value** has one legitimate *non-incentive* use: offline *attribution/debugging* ("which agent's contribution actually moved the needle"), but it is exponential to compute exactly and is a nice-to-have, not core.

### D. Classical MAS, swarm, and stigmergy

The foundational MAS teamwork theories — Cohen & Levesque's *joint intentions*, Grosz & Kraus's *SharedPlans*, and Tambe's **STEAM** — formalize cooperative teamwork via a shared "joint persistent goal" and selective communication. Their key, well-documented weakness is directly relevant: achieving joint belief in large teams becomes a **communication bottleneck**, and STEAM mitigates it only with decision-theoretic *communication selectivity* (communicate a fact only when the expected cost of miscoordination exceeds the cost of the message). **Lesson for the blueprint:** don't make agents broadcast to each other; have them read/write shared state and communicate selectively. This is an argument *against* chatty peer-to-peer agent conversations and *for* a blackboard.

**Stigmergy / ant-colony** coordination — agents leave traces in a shared environment that trigger others' actions, with positive feedback (reinforce good paths) and negative feedback (pheromone evaporation), as formalized by Grassé (1959) and operationalized in Dorigo's Ant Colony Optimization — maps onto a shared ledger/blackboard where completing a ticket "marks the trail" for others. Its documented hard constraint: it works *only when actions are reasonably independent (locality holds)*; otherwise it thrashes. This is the strongest theoretical argument for **decomposing coding work to maximize independence** and for the **blackboard** (Hearsay-II lineage: knowledge sources + shared workspace + control component) over direct messaging.

### E. Complexity/chaos as diagnosis; control theory as cure

"Edge of chaos" (Langton/Packard) and self-organized criticality (Bak) describe systems poised between order and chaos where adaptability is maximal. The honest reading: this is a **metaphor and a warning, not a build spec** — Melanie Mitchell and others have questioned its generality. The actionable cousin is **control theory**: treat the agent fleet as a plant under feedback control. CI/tests are the *sensor* (observability), the merge gate is the *actuator/controller* (it rejects regressions), and a concurrency governor provides *backpressure* (Gastown's Scheduler is exactly a rate-limit governor). The goal is a *stable-but-adaptive* regime: enough parallel exploration to be fast, enough gating to stay correct. Gastown's reported chaos ($100/hr burn, auto-merged failing tests) is precisely a *control failure* — the actuator (merge gate) wasn't strict enough, so the loop went open.

### F. Prior art — what already exists (don't reinvent)

- **Orchestrator-worker (Anthropic Research; Claude subagents).** A lead agent plans and spawns parallel subagents with isolated context windows that return condensed results; workers don't talk to each other. Per Anthropic Engineering, "How we built our multi-agent research system" (Apr 2025), "a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval"; such systems "use about 15× more tokens than chat interactions," and the approach is explicitly *not* a good fit for "domains that... involve many dependencies between agents." **This is the simplest sound topology and the recommended default**, with the caveat that coding needs the merge-queue addition.
- **LangGraph** — graph/state-machine orchestration (explicit nodes/edges, durable execution, human-in-the-loop). Best fit for the "boring, explicit, debuggable" preference. **Strong candidate as the implementation substrate.**
- **AutoGen/AG2** — conversational peer-to-peer agents; flexible but emergent and harder to reason about (chatty, prone to the inter-agent-misalignment failures). **De-prioritize for a "boring" system.**
- **CrewAI** — opinionated role/process abstraction (simulates a crew); easy but prescriptive. **OK for quick starts, but it re-imports the org-chart framing.**
- **OpenAI Swarm → Agents SDK** — minimalist primitives (Agents, Handoffs, Guardrails); Swarm was explicitly educational, the Agents SDK is the productionized successor. **Good minimalist reference.**
- **MetaGPT/ChatDev** — encode a software-company org chart (PM→architect→engineer); research-grade, demonstrate verifier agents help (MetaGPT reports a meaningful success-rate gain from explicit reviewers). **These are the clearest examples of the org-chart trap; mine them for the verifier idea, not the structure.**
- **Protocols: MCP (Anthropic, tools/context, Nov 2024) and A2A (Google, agent-to-agent, Apr 2025, now under Linux Foundation governance).** MCP = vertical (agent↔tools); A2A = horizontal (agent↔agent). **Adopt MCP for tool access; A2A only if you federate across orgs.**
- **Verification methods**: multi-agent debate and LLM-as-judge improve factual accuracy, but per Huang et al., "Large Language Models Cannot Self-Correct Reasoning Yet" (ICLR 2024, arXiv:2310.01798), multi-agent debate's "efficacy is no better than self-consistency... when considering an equivalent number of responses," with gains coming from "consistency" rather than genuine "self-correction." **Implication: prefer objective verifiers (tests) over agents judging agents.**

### G. Hierarchical vs. alternative topologies — tradeoffs

- **Hierarchical supervision (Gastown).** + Clear control, good observability, natural failure escalation. − Anthropomorphic role sprawl, central bottleneck, many tiers to operate/debug, brittle when the metaphor leaks. *Verdict: keep one supervisor level for restart; drop the multi-tier command chain.*
- **Flat orchestrator-worker.** + Simplest mental model, parallel, proven (Anthropic), constrains topology so it's debuggable. − Orchestrator is a single point of failure (mitigate with restart), weaker for tightly-coupled tasks. *Verdict: recommended default.*
- **Peer-to-peer / swarm (AutoGen).** + Flexible, no bottleneck. − Hard to reason about, chatty, prone to misalignment failures. *Verdict: avoid for a boring system.*
- **Blackboard / shared-state.** + Decouples agents (add/remove freely), great observability, matches event-sourcing you already need, naturally implements selective communication and stigmergy. − Needs a control/scheduler component to pick who acts; potential contention on the store. *Verdict: adopt as the coordination substrate.*
- **Graph/dataflow (LangGraph).** + Explicit, testable, durable, supports cycles and gates. − You must design the graph. *Verdict: best implementation substrate for explicit pipelines.*
- **Market/auction.** + Self-balancing allocation. − Assumes self-interest you don't have; overhead. *Verdict: use only the capability-routing skeleton, no real bidding.*

## Recommendations

**Stage 1 — Build the minimal correct core (this is 80% of the value).** Adopt exactly these primitives:
1. **Durable shared log/ledger** (git-backed, event-sourced — keep Beads-style state) as the single source of truth. This gives crash recovery + observability + the blackboard.
2. **Content/intent-addressed work tickets** with **idempotency keys**. Re-running a completed step is a no-op. Directly kills Step Repetition (15.7% of failures).
3. **Optimistic parallel work in isolated worktrees** (eventual consistency for scratch) + **one serializing merge queue with hard CI gates** (linearizability for `main`). Nothing merges that fails tests. This is Gastown's Refinery, kept.
4. **Flat orchestrator-worker spawning** with **work-stealing** (idle agents pull ready tickets). No "Mayor" pushing assignments; no role personas.
5. **A single failure detector + crash-only restart from the log.** Heartbeat/no-progress timeout → kill and restart the agent from durable state. Replaces Witness/Deacon/Dogs/Boot with one supervisor.

**Stage 2 — Add verification leverage where correctness isn't auto-checkable.**
6. **Best-of-N with a real verifier** (tests/compiler first; a judge/diversity-based selector only when no objective signal exists). Avoid naive majority voting (popularity trap).
7. **Conventions as Schelling points** (canonical file/layout/naming rules in the system prompt) to cut inter-agent misalignment without adding communication.

**Stage 3 — Only if you actually hit these limits:**
8. **Leader election** for the orchestrator — only when you run multiple coordinator nodes.
9. **Gossip + logical clocks + A2A** — only when federating across machines/orgs (the Wasteland use case).
10. **Explicit SAGA compensations** — only for multi-system side effects git can't revert.

**What to delete relative to Gastown:** the persona/role hierarchy (Mayor, Crew vs. Polecats as *social* roles), the multi-tier escalation chain (Deacon→Mayor→Overseer), and the watchdog cast (Witness/Deacon/Dogs/Boot) — collapse all of it into *one failure detector + one supervisor + one merge queue*. Keep: the git-backed event-sourced ledger, the merge queue, worktree isolation, and the concurrency governor.

**Benchmarks/thresholds that change the plan:**
- If your tasks are *tightly interdependent* (high cross-module coupling), parallelism and stigmergy stop paying — *reduce agent count and serialize*, because Anthropic's own data says multi-agent is weak for interdependent coding.
- If **token cost** matters more than latency, drop best-of-N to best-of-1 with a verifier loop (multi-agent runs ~15× the tokens of a single agent).
- If you measure **merge-queue rejection rate climbing**, your decomposition has poor locality — re-decompose for independence before adding agents.
- If agents are **same-model**, distrust voting (correlated errors) and lean on objective verifiers.

## Caveats
- **Gastown is ~5 months old, fast-moving, and "100% vibe coded" by its author's own admission.** Specific mechanisms (heartbeat intervals, Dolt backend, Wasteland) are described from its docs and secondary coverage as of mid-2026 and may have changed. Treat its internals as a moving target.
- **The 90.2% Anthropic figure is an internal research-task eval, not coding**, and comes at ~15× token cost; Anthropic explicitly warns multi-agent underperforms on interdependent coding. Do not over-generalize it to a coding orchestrator.
- **"Aligned agents" is an assumption, not a guarantee.** If agents are prompt-injectable or models drift, the Byzantine/verification primitives become *more* important, not less — which is why the merge gate and verification stay non-negotiable even in the minimal design.
- **Voting/debate has real but bounded value**: a rigorous comparison (Huang et al., arXiv:2310.01798) found it no better than self-consistency at equal cost, and self-correction without an external signal is unreliable. The objective verifier (tests) is the thing that actually works.
- **Complexity/chaos theory should not be implemented literally.** Its value here is diagnostic (why hierarchy is brittle and pure swarm is chaotic); the engineering realization is ordinary control theory (feedback, backpressure, observability), which is the "boring" technology the user prefers.
- This report weights toward **minimal, production-proven mechanisms** per the user's stated preference; a researcher optimizing for novelty or peak benchmark scores might rationally choose more aggressive ensembling or learned orchestration (e.g., GPTSwarm/DyLAN-style self-organizing graphs), at the cost of the simplicity and debuggability prioritized here.
